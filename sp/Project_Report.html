AI-Based Student Behaviour Analysis & Engagement Prediction System

Complete Project Report

Flask • SQLAlchemy • scikit-learn • OpenCV — Programming Laboratory Engagement Analytics

1. What It Is

A Flask web application for programming laboratory sessions. It records student behaviour across four "modalities" — visual (gaze/webcam), programming activity (typing, editing, code runs), timed alert questions, and a final MCQ assessment — then produces an engagement score and classifies each session as High, Moderate, or Low Engagement. It provides a Student portal and a Teacher analytics portal.

2. Technology Stack

  • Backend: Python, Flask 3, Flask-SQLAlchemy, Flask-Login, Flask-WTF
  • Database: SQLite (database/app.db) via SQLAlchemy ORM
  • ML / Data: scikit-learn, pandas, numpy, joblib
  • Computer Vision: OpenCV (opencv-python)
  • Frontend: Jinja2 templates, Bootstrap, Font Awesome, Chart.js, vanilla JavaScript
  • Security: Werkzeug password hashing, CSRF protection, role-based access decorators

5. Complete User Flow

Student

  1. /student/dashboard — shows past sessions and a "start new lab" action.
  2. /student/start — chooses Python or C and gives camera consent; creates a LabSession plus 5 LabTaskAttempt rows.
  3. /lab/<session_code> — workspace with the 5 tasks: write-from-scratch, arrange jumbled code, fill-in-the-blank, debug, predict output.
  4. Run code via /lab/<code>/run (subprocess execution, 5-second timeout).
  5. Submit tasks via /lab/<code>/submit-task; auto-checked against expected output or correct option.
  6. Timed alert questions fetched via /alert/get, answered via /alert/respond (300-second timeout).
  7. Gaze telemetry posted every 6 seconds to /telemetry/gaze.
  8. Activity telemetry (keystrokes/edits) to /telemetry/event.
  9. After all 5 tasks → tasks-completed → 10-question MCQ assessment → submit.
  10. On assessment submit the session is marked completed, then EngagementPredictor.predict_session_engagement() runs.
  11. /student/result/<code> — simple confirmation; AI scores are hidden from students.

Teacher

  • /teacher/dashboard — KPIs (students, sessions, completed, active), engagement doughnut chart, session list.
  • /teacher/session/<id> — per-session deep dive: tasks, code and outputs, activity summary, gaze scatter plot and screen-area breakdown, alert responses, assessment review, prediction scores/confidence/warnings.
  • /teacher/student/<id> — per-student history.
  • /teacher/reports — aggregate engagement counts.
  • /teacher/export/csv — full CSV export of sessions and predictions.

7. How Engagement Is Computed

FeatureExtractor.extract_session_features() aggregates four groups of features:

  • Visual: face visibility %, editor / instructions / console / outside attention %, average fixation (only if more than 5 observations and face detected above 10%).
  • Programming: edits, keystrokes, tasks completed/passed, task time, idle count, run count.
  • Alerts: total / answered / timed-out / correct, average response time.
  • Assessment: score, percentage, completed flag.

Then EngagementPredictor.predict_session_engagement() computes four 0–100 sub-scores and a weighted fusion:

  1. Visual = editor×0.6 + face×0.3 − outside×0.2 (skipped, not penalised, if camera is missing or declined).
  2. Programming = (tasks/5)×50 + min(35, keystrokes/150×20 + edits/30×15) + min(15, runs×5).
  3. Alert = answered_ratio×60 + correct_ratio×40.
  4. Assessment = assessment percentage.

Weights dynamically renormalise based on available modalities (for example, with visual data present: visual 0.25, programming 0.35, alert 0.15, assessment 0.25). Classification thresholds: High ≥ 70, Moderate ≥ 42, otherwise Low. Confidence = 0.55 + 0.1 × active_modalities (capped at 0.98). Results are stored in engagement_predictions.

8. Machine Learning Model & Important Caveat

Split80/20 stratified → 400 train / 100 test
Reported metrics100% test accuracy, macro F1 = 1.0, perfect confusion matrix
Top featureskeystrokes 0.317, edits 0.139, outside-attention 0.135, tasks 0.113, editor-attention 0.095
Accuracy caveats:
  • The 100% score is expected because the synthetic labels are trivially separable from the features; it does not reflect real-world accuracy.
  • evaluate_model.py re-evaluates on the full 500 rows including training data — a data-leakage problem.
  • The trained model is never used at runtime. load_model() loads the .pkl, but predict_session_engagement() never calls it. Live predictions are entirely rule-based.

9. Webcam / Gaze — Real vs Simulated

  • The browser requests the webcam with consent and draws frames to a canvas every 6 seconds, but does not send images — it sends numeric gaze values.
  • Those values are randomly generated in JavaScript (Math.random() jitter around x = 0.65, y = 0.40), not actual eye tracking.
  • modules/webcam.py (real OpenCV Haar-cascade face detection) and modules/facial_features.py (head-pose math) exist but are never called.
  • ScreenAreaMapper classifies coordinates into editor / instructions / console / outside / unknown, but only from the simulated coordinates.
  • No video or images are stored anywhere; datasets/raw and datasets/processed are empty.

10. Security Features & Weaknesses

Implemented

  • Passwords hashed with Werkzeug; role-based decorators student_required / teacher_required; login redirect validation.
  • Code executor blocks strings such as os.system, subprocess., shutil.rmtree; runs in a temp directory with a 5-second timeout.

Weaknesses

  • The string-based sandbox is easily bypassed and is not safe for public or untrusted use.
  • SECRET_KEY is hardcoded in config.py; debug=True is used in app.py.
  • No rate limiting; students can self-register as teachers.

12. Honest Summary of Limitations

  1. Synthetic-only data — no real DAiSEE / video / student dataset, despite a docstring mention.
  2. Simulated gaze — visual "engagement" is random values, not actual eye tracking.
  3. Trained Random Forest is unused — runtime is rule-based; the 100% accuracy is an artifact of synthetic data and leakage.
  4. Not production-ready — insecure code sandbox, hardcoded secret, debug mode, no HTTPS, no migrations.
  5. Some modules (webcam.py, facial_features.py, dataset_preprocessing.py) exist but are unused.
